
### Motivation

Leaf builds on a broad body of [research](bibliography.md) in quantum programming languages. Our goal is to create a practical language that enables users to write useful quantum programs easily and safely for tomorrow’s fault-tolerant quantum computers.

### Starting point

Leaf is deliberately designed to replicate Rust’s basic syntax, with conservative extensions for quantum programming which are meant to look and feel like Rust. It follows Rust’s philosophy of strong static type support and extends it to [quantum data](defining-terms.md#what-is-quantum-data) and both unitary and non-unitary [quantum operations](defining-terms.md#what-are-quantum-operations). While the classical fragment follows Rust-like operational semantics, quantum data and quantum operations represent a significant departure from ordinary Rust code. Following the Rust philosophy, the compiler provides detailed error diagnostics and warnings, which makes the language friendly to interactive AI-assisted code generation.

More precisely, Leaf is intended to be a statically typed and safe language. This means that types are checked by the compiler before execution. We aim to build a sound type system which ensures that well-typed programs come with formal guarantees that they behave according to the language’s semantics, without undefined behaviors, type-related execution errors, or attempts to perform non-physical quantum operations, enjoying ancilla qubits management and automatic uncomputation support. Safety ensures that bad runtime behaviors are ruled out by the type system.

### Compilation lifecycle of Leaf code

1. Frontend - lexes and parses Leaf source, validates and desugars its syntax, resolves names, and checks types, ownership, and effects to produce a checked AST.
2. Lowering to Core - translates the checked AST to a small, typed IR based on quantum lambda calculus.
3. Lowering to DSL - translates Core to the circuit-oriented IR implemented as an Idris2 DSL.
4. Backend - emits the target representation from the DSL:
   - OpenQASM3 for now.
   - QIR to be added later.

The planned exporter provides another output path from the DSL: it generates
Lean definitions for formal verification under `Compiler/Exporter/`.

### Source layout

```text
src/
├── Core/                       # Quantum lambda-calculus IR definitions
├── DSL/                        # Circuit representation, builders, and examples
├── Compiler/
│   ├── Frontend/
│   │   ├── Lexer/
│   │   ├── Parser/
│   │   ├── Syntax/
│   │   ├── Validation/
│   │   ├── Desugar/
│   │   ├── ScopeAndNameResolution/
│   │   ├── TypeChecker/
│   │   └── Utils/
│   ├── Lowering/
│   │   ├── ToCore/
│   │   └── CoreToDSL/
│   ├── Backend/
│   │   └── OpenQASM3/
│   └── Exporter/               # Planned DSL-to-Lean export
├── Leaf.idr                    # REPL entry point
└── Main.idr                    # Command-line entry point
```

`Core` and `DSL` own their representations and intrinsic operations. They do
not import compiler passes or each other. `Compiler.Lowering.ToCore` will
depend on the checked frontend AST and Core; `Compiler.Lowering.CoreToDSL`
will depend on both Core and DSL. Backends and the Lean exporter consume
the DSL; the DSL does not depend on either of them. The frontend's
shared source locations, tokens, AST metadata, quantum annotations, and
prelude definitions live directly under `Compiler/Frontend/`.

### Formal verification support

Leaf will support formal verification by combining static type checks across multiple IR levels with a **Lean** interface for proving program properties:

- Type safety is ensured by a strong static type system at both the surface-syntax level and the typed high-level IR, with rigorous coverage of quantum operations and their physical constraints.
- An attempt will be made to track entanglement at the level of type system using pre & post-condition function annotations. When a condition cannot be checked statically a Lean proof obligation will be generated by the compiler.
- The developer will have the tools to test the semantic correctness of their program by writing Lean proofs at the level of the high-level IR representation of the quantum algorithm.
- The quantum gates & quantum circuit oriented Idris DSL intermediate IR representation provides additional support for Lean verification of unitary fragments of quantum code.
- `Compiler/Exporter` will export the DSL representation to Lean for this verification work.
- Correctness of language lowering: the translations to the Idris DSL and subsequently to OpenQASM3/QIR should preserve the semantics of the high-level IR (denotational semantics preservation).

The Idris2 DSL does not enforce a full typing discipline, but it is equipped with correctness guarantees expressed using Idris2’s dependent type system and built-in proof support, ensuring that qubit indices used in gate applications are valid, control qubits are distinct from target qubits, and all control/target qubits are pairwise distinct when multiple qubits are involved. This is an extra check in the spirit of LLVM -verify pattern.
